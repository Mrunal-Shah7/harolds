What this file is now

v1.1 was a proposal. This is a record. The CSS in the three style blocks is lifted verbatim from globals.css, admin.css and kitchen.css; only Tailwind's own @import, @theme and @layer wrappers were converted, because they mean nothing outside the build. Resize the window and this file breaks exactly where the app breaks, because the media queries are the app's.

What shipped from the v1.1 proposals

  • 1. Weave texture as zero-asset CSS. Shipped. Two crossed 1px repeating gradients at 3.5% ink on light band roots. No asset, no request, no CSP change.
  • 2. Board leaders. Shipped. The dotted rule binds a name to a figure in totals and receipt contexts: checkout, confirmation, the hours sheet, admin order detail.
  • 3. Chip construction. Shipped. Real notched corners via clip-path, the dashed flame rule following the notch. Still the only dashed border in the system.
  • 4. Poster face. Shipped as Alfa Slab One, self-hosted subset WOFF2 alongside Baloo 2, Inter and JetBrains Mono. No external font origin is contacted and the CSP was not widened.
  • 5. Hero voice. Shipped. Three stacked poster lines, one brand-red accent line.
  • 6. Storefront dark scheme. Shipped, opt-in, light by default, behind the labelled header toggle. Admin stays light; the KDS scope shares no token with it.

    • Latest round — a re-numbering bug, and the back office

  • The storefront learned to answer sooner. A live search filters the menu already in memory, so results land on the same frame as the keystroke and cost the store no requests. A card whose item is in the cart shows a stepper instead of “Add”, and the cart bar carries a running items figure. That figure is the one place the storefront shows money it did not get from a quote: it is an estimate, labelled Items rather than Total, excludes tax and tip, is never sent back, and is superseded by the checkout quote. The cart gained per-line instructions and a skippable sides-and-extras step in the same sheet, and checkout gained a whole-order instruction that prints on the ticket, a way back that is not the browser’s, inline field validation, and a custom tip that moves the total as it is typed rather than on blur — which is why it appeared to be ignored. Admins can cap how many of one item an order may contain; the cap is enforced in validateCart, summed across the whole cart, because a limit only the UI honours is not a limit.
  • Two slips became one, and the receipt email started arriving. Every order queued a kitchen ticket and a counter receipt. Both went to the same physical printer — kitchenSerial and counterSerial both fall back to the one configured serial — so each order produced two pieces of paper that staff paired up by hand. They are now a single receipt carrying the kitchen’s identity block and items plus the money and the card that paid it. It keeps the KITCHEN_TICKET target because acknowledging that target is what moves an order PAID → PRINTED. Separately, receipt email was never arriving: the pipeline was built and the job was being queued, but EMAIL_FROM_ADDRESS was a gmail.com address and Resend only sends from a domain you have verified, so every send came back 403.
  • A collected order still said “We’re on it”. The status page branched on a status called COMPLETED — a value the enum does not contain and the kitchen can never set. The real one is PICKED_UP, so a collected order fell through stepIndex’s default arm to −1 and blanked every point on the timeline: the customer watched their finished order revert to three empty circles. The page now speaks in three tenses — preparing, ready, picked up — with the last timeline point named for where the order actually got to, and pickedUpAt carried through the public contract so the thank-you can name the time.
  • An order could be re-numbered after the kitchen finished it. The capture path short-circuited only when status === PAID, so once the kitchen moved an order on, a redelivered Square payment.updated webhook fell through the guard, allocated a SECOND order number and reset the order to PAID — a customer watching the status page saw HC-001 become HC-002, and the ticket returned to the board. Both guards (the allocator and the webhook) are now keyed on the PAYMENT, never on fulfilment progress. Pinned by a regression test that fails 4/5 against the old code. The same status-as-idempotency-key mistake sat in the webhook's failure branch, where a redelivered payment.failed for a superseded attempt could flip a captured, already-cooking order to payment-failed; both branches now key on the payment.
  • Reports: gross and net were the same number. Gross was the order total (tips included) and net was that minus refunds, so with no refunds the two tiles agreed. Gross is now food + tax and net is gross − tax; tips belong to staff and refunds are their own line, and neither moves either figure. Each tile prints its own definition.
  • Selecting a tip destroyed the card field. The Square mount effect had the display total in its dependency array, so every tip change tore down the card iframe and re-attached it — the input vanished on some selections and returned on others. The total now lives in a ref: the card mounts once. Card is the only payment method offered for now; the wallet code is hidden behind a flag, not deleted.
  • One floating save bar, for every form. The admin forms are long and an inline Save sat below the fold, so a change could be typed and lost. Every form now hands its Save to a bar that rises when the form is dirty and is absent when it is clean — its presence is also the answer to “did that save?”. It names the form it belongs to, and bars portal into one host so several dirty forms stack rather than pile up.
  • Categories moved to their own screen. They were an accordion above the item filters, so the Menu screen carried two unrelated tables and a create form. Menu is now just items plus a filter panel; Categories has room for its create form, rail images and activation.
  • Dropdowns are ours now. A bare <select> rendered as the OS control and ignored every token in the file. They take the same body, border and radius as a text input, with one ink chevron drawn as a background image — a replaced element cannot host a pseudo-element. Multi-selects keep the native list, having no arrow to draw.

    • Latest round — brand, delivery, and SMS off

  • The logo replaces the text wordmark. The header carries logo.jpeg at 40px tall (34 on a phone), sized by height because the lockup is 2.24:1 and any fixed width would squash it. The favicon is the running man cropped out of that lockup and letterboxed square — the full mark is illegible at 32px.
  • Light only, for now. The header toggle is gone and the app stamps data-theme="light" on <html>. The dark scheme and lib/theme.ts are still in the tree, unreferenced; stamping light is also what stops a visitor whose OS prefers dark from landing on it. Removing the toggle handed its margin-left:auto back to the cart button, or the header would bunch left.
  • Hero banner, set from admin. StoreConfig.heroImageUrl, served additively on /api/v1/store/status. Present, the band gets a full-bleed background and a paper-tinted scrim — the design had no scrim element, and without one a 4.5rem poster headline over an arbitrary photograph is unreadable. Absent, the hero is the plain paper band the design draws.
  • Category rail images, set from admin. Category.imageUrl, same content-addressed pipeline as a menu item's photograph rather than a second uploader. The first initial is now the FALLBACK, not the default.
  • Delivery beside pickup. Secondary button, new tab, straight to DoorDash. It leaves the site, so it does not take the primary.
  • SMS is hidden, not removed. The consent checkbox, the “we text this number” help line, “we'll text you the moment it's up” and “check your texts” on the payment-failure path are all gone; the receipt line now says email only. Phone stays REQUIRED — the counter still needs a way to reach someone — with the copy changed to say why. smsConsent is still sent, always false: the order contract and the notify package are untouched, so re-enabling is a checkbox, not a migration.
  • Burnham, not Oak Lawn, in every string, title, manifest and seed. The street address and ZIP are unchanged. One print test had to be re-centred by a single space, because “Burnham” is a character shorter and the receipt centres its store name.
  • “75 years loud” replaces “Fifty years loud” in the hero's accent line, and the footer drops “Pickup only, paid online, ready when we text you”.

    • What the implementation added that v1.1 did not draw

  • A responsive layer. Two axes, deliberately separate: (pointer: coarse) raises every tap target to 44px and drops hover affordances, keyed off input rather than width so a touch tablet gets it too; max-width queries reflow. Below 768px the status pill takes its own row under the header, the category rail bleeds to the screen edge, overlays go full-width, and the cart bar renders a spacer so it never covers the last card. Below 400px the wordmark drops its mono subline and the header's paddings tighten — measured to fit at 320px.
  • The header pins by measurement, not by constant. --sf-header-h is published from the header's real height by a ResizeObserver; the sticky tab bar reads it and the scroll-to-section handler subtracts it. The two hand-kept constants this replaced had already drifted 5px apart from the CSS.
  • Most ordered is curated from the Menu table. A toggle on every row, beside Sold out. The list is hand-picked, not a sales figure, and an empty list hides the storefront band entirely. The Curation page now manages Featured only — two controls for one list is how the two disagree.
  • The kitchen board is one grid, not three status columns. Cards are ordered by age and each carries its own next action. This is the one change that alters how expo staff scan the board during a rush.
  • An explicit audio-unlock panel over the board, because Android will not play the chime until the page has been touched once.
  • Screens v1.1 never drew: admin sign-in, Dashboard, Modifiers, Store, Jobs, Staff and the item and group editors; the kitchen PIN pad and cancel confirmation; the storefront's hours sheet, route-level skeletons, error state and undo toast. All are built from the design's own primitives — no new visual language.

    • Deliberate departures, and why

  • Checkout takes first and last name, and an SMS-consent row. v1.1 drew a single "Name" field. The required set predates the design and changing a validation rule is not a design change.
  • The checkout summary is NOT reordered above the form on mobile. order moves a grid item visually without moving it in the DOM, so a keyboard or screen-reader user would traverse a payment form in a different order than they see it.
  • No "New" corner badge. v1.1 drew one on a most-ordered card. There is no isNew field on a menu item, so the slot carries SOLD OUT only.
  • The cart carries no money. Line totals would ignore modifier surcharges. The only lawful source of a total is the server quote, and the storefront quotes at checkout.

    • Placeholders still in force

  • Text wordmark in Alfa Slab One, brand on paper — no logo yet.
  • #CE1126 as brand red, declared once in the token block.
  • Paper-sunk initial tiles in every 4:3 frame — photography exists for a handful of items only.

    • Caveats

  • Fonts load from Google Fonts in this file only; production self-hosts all four faces (font-src 'self').
  • The data here is invented so the file can show states the seeded catalogue has no example of — a sold-out item, a kitchen note, a refunded order, a late ticket. The running app renders the real Harold's catalogue through this same markup.
  • Interactivity is mockup-only. Every figure in the real app comes from the server.
